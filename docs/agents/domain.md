# Domain docs

当前使用单上下文文档布局：根目录 GLOSSARY.md 和 docs/adr/。这只是文档位置约定；限界上下文的数量由领域分析确定。

- 探索代码前，读取已有术语表和与任务相关的 ADR。
- 文件不存在时继续；术语和决策实际确定后再按需建立。
- Issue、代码、测试和设计使用术语表定义的名称。
- 与已有 ADR 冲突时，明确指出冲突及重新讨论的理由。

## DDD 设计

- 先结合 Simulator、支付公司校验的具体排障案例，明确业务语言、行为、业务规则和证据要求；不凭技术组件或仓库数量划分限界上下文。
- 使用 `domain-driven-design` 指导领域边界、聚合、值对象和不变量；使用 `domain-modeling` 维护术语表与必要的 ADR。
- 聚合围绕真实的一致性约束设计，行为与不变量由领域模型表达；简单概念采用最小实现，不为模式或评分增加实体、事件总线、CQRS 或事件溯源。
- 领域层表达业务模型，应用层编排用例，基础设施 Adapter 翻译外部模型；领域模型不直接依赖 Teams、Pi、MCP 或 GitLab SDK 类型。
- 领域设计经业务场景验证后，以 TDD 逐个实现行为和边界条件；通过 Mock Adapter 验证外部交互。
- 如果领域分析确需多个限界上下文，再记录上下文关系并调整文档布局，不提前拆分微服务。
