## Behavior and owned source contracts

The existing A–D operations now carry a scenario union. PSP input selects `scenario: "psp"`, an application or customer identifier, optional shop/binding selectors and a question. The host fixes the log alias and linked repository. A complete trusted discovery can resolve one target or request a `candidateRef` selection from bounded shop/business-binding candidates. Candidate selectors remain server-owned after sanitization. Current owner, resource authorization, question/Teams receipt association, original cumulative limits and new-phase semantics are preserved. Replies cannot replace a supplied application/customer/shop/binding; changing the object requires a new case. The selected customer and related binding record cannot drift on a later read.

`PspObservation` is an **owned synthetic diagnostic contract**, not verified production PSP field/state names. It separates shop/business record/PSP binding, first match, independently evidenced combination-support basis/version/effective and observation times, applicable transaction and tail-three checks, final source determination, reliably linked shop outcomes and correlated branch events. Supported, unsupported and unknown remain distinct; unsupported second-step applicability is never executed/passed. Missing support evidence stays unknown. Conflicting current shop outcomes cannot establish a passed-shop prerequisite; a later outcome supersedes an older one for that binding.

One currently evidenced passed shop linked to the same customer/application can meet the PSP initiation prerequisite even while other shops or source completeness remain unknown. A target failure cannot establish customer-wide failure. Actual initiation, approval and available amount are separate unknown fields when no such evidence exists; no amount, recovery time or business mutation is fabricated.

A concrete waiting/missing/failed/timeout/fallback branch requires a cited log execution event after the selected binding and a matching rule/stage/outcome in the exact frozen code commit. The Codebase translator understands only the closed `// @bau-psp-rule {...}` annotation used by the owned synthetic code fixture. This annotation mapping is not a real business-rule mapping or arbitrary code interpreter. Static code alone is not execution proof. Code/business policy conflicts are displayed separately for human reconciliation.

The full sanitized host report remains in canonical model input and C records under the unchanged 24k full-input bound. PSP may select it with exactly `{reportRef,draftVersion}`. The version binds the case, phase and accepted-material revision; extra, foreign and stale selections fail. Output, reasoning and charging retain the existing 4k limit. Simulator full-draft echo and its **all submitted shops**, including 9+1 readiness, remain unchanged.

## Resource and protocol boundaries

The trusted case context contains log sources plus at most **three business repositories across both scenarios**. `simulator-source` retains its legacy combined source/repository meaning; `psp-log-source` is log-only. A model cannot install a source, repository collection, snapshot, query identity or endpoint, and the log-only alias cannot be used as a code repository. The same frozen full context/snapshot reaches every profile and phase. A native code collection must exactly equal the derived approved repository set; whole-collection and per-end current authorization are retained.

The explicit owned Kibana mapping binds `simulator-source` to `synthetic-simulator`, and `psp-log-source` to `synthetic-psp`. PSP compiles exact application/shop/binding and UTC range filters. Its closed rows carry `event_id/event_time/application_id/customer_id/shop_id/binding_id/verification`, with individually associated observation points. The approved index/field mapping is local synthetic data only. Authoritative target discovery remains refused on lossy native Kibana results. Native completeness is always unknown; positive point facts do not establish complete history. Existing native CBM lost cross-service destination semantics remain unknown; construction/index receipts do not manufacture an execution chain.
