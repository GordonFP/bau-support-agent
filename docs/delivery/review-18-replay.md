# #18 评审跟进 — 重启后的重复事件回放

针对 [#18](https://github.com/GordonFP/bau-support-agent/issues/18) 在 `160921b` 的 P2：完成案重启后，第二次重复事件因内存中没有 RunningCase 被拒绝；另有 32 个新案活跃时，首次持久重复事件被容量检查挡住。原始交付与真实启用限制仍见 [#18 记录](issue-18.md)。

修复后，持久重复事件每次均通过 C read 重新检查案主及当前授权，返回保存的受控视图，不恢复调查。现有 admission Port 增加宿主内部可选 lookup，仅按可信事件摘要返回最小案件／主体引用，在新增调查容量判断之前识别持久重复。该扩展已由规格实施协调者确认，A–D 公开测试边界不变。

查找与读取等待按可信事件及主体合并，最多占用 32 个入口控制位置，与待受理操作共享上限；查找与后续受理共用原始 180 秒宿主截止时间，不在查找完成后重置。超时但尚未结束的控制继续计入上限，迟到查找不得启动调查。同一主体在另一租户／会话具有不同事件摘要，其他主体不会共用含视图的查找结果。新调查仍受原有 32 案容量约束。SQLite 容量比较复用既有 `MAX_ACTIVE_CASES`。

按 TDD 先复现重复回放及满额拒绝，再作最小修复；公开边界回归同时覆盖撤权、反复回放、零新增业务动作、等待合并／越界、超时与迟到控制。
