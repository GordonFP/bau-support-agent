# 两个试点场景的排障契约

本文件汇总已确认的业务口径与基于 BRD 的报告要求。它用于后续接口与 TDD 规划，不表示业务源码、日志契约、SDK 或真实环境已经验证；没有实施业务代码或自动化测试。

关联决策：[Simulator 与支付公司校验的排障规则和报告契约是什么？](https://github.com/GordonFP/bau-support-agent/issues/5)。具体规则与合成验收例见 [Simulator](simulator.md) 和[支付公司校验](psp-verification.md)；业务语言见[术语表](../../GLOSSARY.md)。真实资源标识不在这些可审查规划文件中记录。

## 已确认的场景边界

| 项目 | Simulator | 支付公司校验 |
| --- | --- | --- |
| 主要问题 | 本次测额为何迟迟没有结果 | 目标店铺为什么未控 |
| 定位对象 | 本次测额申请及提交时的店铺列表 | 目标店铺、相关业务记录与 PSP 绑定 |
| 输入与澄清 | 客户编号或测额申请编号；多次申请补问提交时间 | 接受目标店铺问题；具体标识由来源契约确认，不能唯一定位时补问 |
| 调查重点 | 授权、各店铺数据完整覆盖日期、测算执行与异常 | 店铺匹配、组合支持能力、适用检查的代码分支和执行结果 |
| 场景条件 | 全部提交店铺的数据齐备才满足估额前置条件 | 至少一家店铺校验通过即满足 PSP 层面的授信发起条件；其余未控影响可用额度 |
| 解释局限 | 数据齐备还需测算执行与结果证据 | 发起条件、审批结果和可用额度分别表达；缺额度证据不计算具体金额 |
| 来源范围 | 用户指定的单一代码/日志来源，使用资源代号 | 用户指定日志来源；仓库、索引及分支映射待确认 |

具体支持清单、匹配规则、缺数据/失败/回退及状态迁移由 Agent 在获准范围内读取固定版本代码，并结合相符日志判断。用户已经确认的业务口径作为比较依据；发现实现不一致时保留冲突及证据，交由人工复核。

## 共用行为与完成标准

1. 定位与澄清：同一客户的不同申请、不同店铺或绑定不能混用；信息不足时明确询问缺失的定位条件。
2. 受控取证：可信身份、会话与资源范围来自服务端；每次调用授权，外部数据在模型前脱敏并按不可信内容处理，保持只读和审计。
3. 解释事实与逻辑：关键事实必须有证据引用；代码给出逻辑依据，日志说明观察到的执行，不把可能分支写成已执行事实。
4. 保存版本：代码证据记录 Repository、Branch、Commit、文件位置和索引时间；日志记录查询范围与观察时间。过期、不完整、冲突或版本不明的证据保留局限。
5. 形成报告：包含问题摘要、已验证事实、可能原因、证据、置信说明、局限和人工下一步；向目标受众交付前校验披露范围。
6. 可靠降级：无法查询、无权限、数据缺失或依赖失败时不推断根因，不通过扩大权限、写业务数据或自动执行修复来补救。

诊断结论状态沿用 BRD：

| 状态 | 报告要求 |
| --- | --- |
| 已定位 | 与目标问题对应的关键事实和因果解释有足够证据，可复核 |
| 有待验证的线索 | 已有可追溯事实或代码线索，但关键关联仍需验证；注明缺口 |
| 证据不足 | 无法形成有用的受支持判断；说明缺失信息、访问限制或依赖问题 |

上述是排障报告的结论状态，业务系统的测算、校验与审批原始状态另行展示。证据不足的报告也可完成一次排障响应，但不计作已定位根因。

## 领域模型与外部契约的责任草案

- 共用排障模型表达调查对象、请求上下文、证据、事实/推断、结论与局限；证据支持要求适用于两个场景。
- 两个场景保留各自的检查点和汇总口径，复用取证与报告行为；不统一为“全部店铺通过”，也不因技术服务不同而直接拆分限界上下文或微服务。
- 领域模型不直接使用 Teams、Pi、MCP、GitLab 的 SDK 类型。身份验证、MCP 连接、来源字段翻译及同步索引属于相应外部契约；接口细节在后续模块设计决策中确定。
- 业务系统现有逻辑由代码和日志解释；匹配、测算、额度和审批的业务执行仍由原系统负责，BAU Agent 保持只读诊断。
