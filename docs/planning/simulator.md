# Simulator 排障：业务规则与验收草案

状态：业务规则已由用户确认；报告字段与合成验收例为设计草案。尚未读取业务源码或日志，未验证实际字段、状态、接口或运行行为。

关联决策：[Simulator 与支付公司校验的排障规则和报告契约是什么？](https://github.com/GordonFP/bau-support-agent/issues/5)。本文件只记录 Simulator；支付公司校验见[对应草案](psp-verification.md)。

## 已确认的业务规则

- Simulator 是模拟水位计算的流程。客户在征信页提交店铺列表后，系统基于这些店铺的数据进行估额。
- 典型提问来自客户经理或产品运营：测额为什么耗时较长、为什么尚未出结果。
- 支持客户编号或测额申请编号。客户存在多次申请时，补问提交时间以明确目标，不自动取最近一笔或混合不同申请的证据。
- 以本次申请提交的店铺列表为调查对象，数据需要完整覆盖到本次提交当日；目标日期不随后续提问日期向后移动。
- 本次提交的全部店铺均满足数据要求，才满足出估额结果的数据前置条件。一家未满足，即不能把整次申请的数据状态判为齐备。
- 数据齐备表示数据前置条件满足；判断测算完成仍需执行和结果证据。
- 电商平台接口限频可能使抓取较慢；客户在抓取完整前取消授权，也可能影响抓取。某次申请的具体原因仍需对应证据。
- 人工排查通常先检查店铺授权，再检查数据覆盖日期，继而调查测算过程与程序异常。
- 当前场景的源码与日志范围为用户已确认的单一来源。本文用资源代号 `simulator-source` 表示，不记录真实业务仓库标识；该范围不构成生产访问批准。

## 诊断与证据要求草案

1. 明确申请：关联客户、目标申请、提交时间及当次店铺列表；存在歧义先补充信息。
2. 检查授权：按店铺记录可证实的授权状态和证据时间；缺失、历史或冲突证据保持未知，不用姓名或店铺显示名猜测关联。
3. 检查数据：对比每家店铺的实际完整覆盖日期与目标日期，区分满足、未满足、无法确认；单条最新数据或日志更新时间不能自动证明连续数据齐备。
4. 检查测算：关联同一次申请的测算状态、异常与结果证据。授权、抓取与程序问题可以并存，不强制归为唯一原因。
5. 解释卡点：数据未齐时列出受影响店铺与缺口；只有存在相应证据时，才归因于限频、授权取消或程序异常。
6. 关联代码：用已确认分支和固定 Commit 的逻辑解释日志，不把代码中的可能路径当作本次已经执行的事实。
7. 给出建议：根据已证实的卡点提出人工下一步；恢复授权后是否自动续算、是否要重新提交，须依据现有逻辑确认。不编造剩余耗时或承诺恢复。

## 报告字段草案

| 字段 | 内容 |
| --- | --- |
| 问题与申请 | 脱敏客户/申请引用、提交日期、提问及查询时间范围 |
| 数据前置条件 | 本次店铺总数、满足/未满足/未知数量；未知不能计入满足 |
| 受影响店铺 | 授权状态及观察时间、目标日期、实际覆盖日期或未知、对应证据 |
| 已验证事实 | 日志能证明的状态、抓取缺口、测算执行与结果；每项关键事实有引用 |
| 可能原因 | 限频、授权问题或程序异常的支持证据，以及仍待验证的关联 |
| 证据与版本 | 日志定位信息；代码 Repository、Branch、Commit、文件位置、索引时间及新鲜度 |
| 局限与建议 | 缺失或冲突证据、版本局限、下一步动作和人工升级角色 |
| 诊断结论状态 | 已定位 / 有待验证的线索 / 证据不足；与业务系统原始状态分别表达 |

具体业务信息仅向通过资源读取和报告披露授权的用户或会话交付；授权规则由对应安全决策确定。

## 合成验收示例草案

以下均为后续测试设计输入，尚未编写或执行测试，也不代表真实案例。

| 示例 | 预期可观察行为 |
| --- | --- |
| 客户存在两次提交，提问只给客户编号 | 请求补充提交时间，不把两次店铺列表或日志合并，不自行选最近一次 |
| 18 日提交 10 家店铺，9 家完整覆盖到 18 日、1 家到 17 日 | 说明数据未齐，指出该店铺与日期缺口，不声称全部具备出结果条件 |
| 上述申请在 19 日被询问 | 继续使用该次提交的 18 日作为目标，不改成提问当日 |
| 某店铺未抓取完整，且同次申请有相符的授权取消证据 | 分别报告授权与数据缺口事实，解释其关联依据；恢复方式不作未经核实的承诺 |
| 数据未齐，但没有限频证据 | 报告数据缺口和原因待查，不把平台限频写成已确认原因 |
| 所有店铺数据齐备，但既无结果也无明确异常证据 | 说明数据前置条件已满足，继续调查测算阶段；不直接认定程序故障 |
| 同次申请出现明确异常，相关代码能解释触发条件 | 引用异常和固定版本逻辑，区分事实、推断和仍待核验的根因 |
| 授权、覆盖日期、当次列表或日志不可得，或证据相互冲突 | 明确缺失与冲突，保留未知，按证据不足降级；不绕过权限或新增数据库访问 |

## 待验证依赖与人工输入

- 单一来源的日志能否关联客户、申请、当次店铺列表、授权事件、完整覆盖日期、测算执行与结果。授权或抓取状态仅存在于其他数据源时，须明确能力缺口并重新讨论接入范围，不默认扩大权限。
- 实际业务日期的时区、覆盖完整性的判定字段、日志延迟、分页及缺失语义，需由获准的代码与合成契约验证确认。
- 授权取消与抓取完成的时序、恢复后的续算行为，以及当前状态与历史日志之间的关系，需查验现有逻辑。
- 异常代码、日志与当前运行版本的证据强度；历史运行版本无法确认时明确限制，POC 不建设完整部署版本映射。
- 报告字段和验收例仍待共同评审；支付公司校验的未决问题记录在对应草案。
