# 支付公司校验：业务规则与验收草案

状态：基本流程、目标店铺层面的排障诉求及授信发起条件已由用户说明；具体分支交由 Agent 根据获准代码逻辑与执行证据判断。报告和合成验收例为设计草案，尚未读取业务源码或日志，未验证实际字段、状态或运行行为。

关联决策：[Simulator 与支付公司校验的排障规则和报告契约是什么？](https://github.com/GordonFP/bau-support-agent/issues/5)。

## 已确认的基本流程

- 进入正式授信审批流程之前，前面提交测额的店铺需要绑定用于回款的 PSP 账户。PSP 指支付公司。
- 第一步：系统根据 PSP 返回的数据，匹配客户提交的店铺与 PSP 提供的数据。
- 第二步：第一步匹配完成后，根据电商平台账户的回款流水及对应卡号尾三号，与 PSP 流水进行交叉匹配验证。
- 只有部分 PSP 与电商平台组合支持第二步。对不支持的组合，依据第一步结果完成校验状态，不统一要求尾三号校验。
- 适用校验通过后，店铺被认定为可控流；同事通常问的是“某个店铺为什么没控”。“未控”的具体业务状态和原因由现有逻辑及执行证据解释。
- 从支付公司校验这个前置条件看，只需一家店铺校验通过即可提起授信审批；其余未通过店铺影响客户可用额度。不能把某店铺未控直接推断为客户无法发起授信，也不能把能够发起审批等同于审批已经通过。
- 用户决定：第二步是否适用，以及缺数据、失败、超时、回退等具体分支，由 Agent 根据代码逻辑判断，不预设统一的“必须第二步通过”或“可以退回第一步”规则。
- 用户已指定通常调查的日志来源，本文用 `psp-log-source` 代号记录。对应代码仓库、实际日志索引与授权范围仍待映射；日志服务标签不能直接视为代码仓库名或索引名。

## 诊断流程草案

| 检查点 | 诊断需要的证据 | 解释边界 |
| --- | --- | --- |
| 调查对象与绑定关系 | 目标店铺、相关客户/业务申请、平台、绑定 PSP 账户及相关时间 | 以目标店铺问题为入口；无法唯一定位时补充必要信息，具体标识字段待源码/日志契约确认 |
| 第一步店铺匹配 | 输入关联、PSP 返回的数据引用、执行结果与理由 | 不预设匹配字段或自行制定匹配算法，以获准代码与执行证据为准 |
| 第二步适用性 | PSP × 电商平台组合、能力判定依据及其版本/生效时间 | 支持、不支持、尚未确认分别表达；缺配置或缺日志不能证明“不支持” |
| 第二步交叉验证 | 适用时的流水与尾三号匹配执行结果、失败或等待原因 | 根据固定版本代码核实具体分支，并与同次执行日志关联；代码可执行的分支不自动证明本次已经执行 |
| 店铺与客户层面影响 | 目标店铺的现有校验结果、授信发起条件和相关额度规则证据 | 至少一家通过即可满足 PSP 层面的授信发起条件；未控店铺的具体额度影响需要相应证据，不能自行计算或承诺金额 |
| 排障结论 | 事实、可能原因、证据、不确定性和人工下一步 | 基于现有校验执行证据解释卡点；缺证据时不代替系统作审批或校验认定 |

“未通过”“等待”等词在此用于描述待调查情形，不声明现有系统已经使用这些枚举值。

## 已确定的调查方式与剩余验证

- 对支持、失败、缺数据和回退分支不再逐条要求用户预先定义，优先由获准代码取证；缺少相应代码、配置或执行日志时保留未知，不臆造规则。
- 查询以某店铺未控的问题为主；标识关联、绑定变更与重复执行的实际行为由源码和日志确认，定位存在歧义时补问用户。
- 先解释目标店铺，再按用户问题及权限范围说明授信发起和额度影响；其他店铺未查或无权限时，不能推断客户整体状态。
- 代码与用户确认的业务口径不一致时，分别报告业务口径、代码及观察到的执行证据，不静默修改既定业务口径。

## 报告字段草案

- 问题与调查对象：脱敏客户/申请引用、店铺、平台及 PSP 账户引用，避免披露真实账户数据。
- 校验路径：本次组合是否支持第二步、判定证据与时间，第一步及适用的第二步分别给出观察结果。
- 卡点与原因：店铺数据匹配、适用性、交叉匹配执行、结果认定各自能证实的事实；具体异常类型随实际案例与代码验证补充。
- 业务影响：分别说明目标店铺的未控状态、PSP 层面的授信发起条件与可用额度影响；没有全局或额度证据时标记无法确认，不扩大查询权限。
- 证据与版本：日志定位信息、代码 Repository/Branch/Commit/文件位置、索引时间，以及能力判定依据的版本或已知局限。
- 诊断结论：已定位 / 有待验证的线索 / 证据不足，与业务系统的校验状态分别表达。
- 局限与下一步：未知或矛盾证据、仍需人工核验的信息及建议动作，不自动变更校验状态、绑定关系或业务数据。

具体卡号、尾三号和流水的模型可见范围由数据政策决定；建议优先提供脱敏的匹配结果与证据引用，不把原始卡号或完整流水直接发送模型。

## 合成验收示例草案

以下均为后续测试设计输入，尚未编写或执行测试，也不代表真实案例。

| 示例 | 预期可观察行为 |
| --- | --- |
| 第一步出现明确不匹配证据 | 报告第一步的观察结果与依据，不声称第二步已通过，不凭错误字符串猜测根因 |
| 组合不支持第二步，第一步通过 | 说明依据第一步完成状态，并明确第二步不适用，不把它标成已执行通过 |
| 组合支持第二步，存在两步均通过及店铺最终认定的证据 | 分别引用检查点与该店铺结果；授信发起条件另据相关证据解释 |
| 组合支持第二步，但流水缺失、执行等待或匹配未通过 | 查固定版本代码与相符日志解释实际分支，不预设统一回退规则，不自行把该组合归为不支持 |
| 第一步通过，但组合支持情况未知 | 明确适用性证据不足，不把“未发现第二步日志”当作不支持的证明 |
| 同一客户两家店铺，一家已校验通过，目标店铺未控 | 解释目标店铺卡点；据证据说明至少一家通过已满足 PSP 层面的发起条件，其余未控影响可用额度，不报告为必须全部通过 |
| 只取得目标店铺未控证据，未调查其他店铺 | 不推断该客户所有店铺均未通过，也不据此判断客户整体能否发起授信 |
| 未控店铺会影响可用额度，但缺少额度计算证据 | 说明影响类型和证据局限，不估算具体额度变化或将其直接等同于 Simulator 估额结果 |

## 待验证依赖

- 实际匹配字段、流水范围、时间/币种/金额等匹配条件、尾号格式及容错规则，以获准代码和合成契约验证为准，本轮不猜测或重做算法。
- 组合支持清单由配置、代码还是其他获准依据提供，其是否随时间变化、是否在日志中可追溯。
- 现有日志能否关联业务申请、绑定关系、PSP 返回、两步执行及最终状态；缺口需要显式记录，不默认直接访问 PSP 或电商平台接口。
- 卡号及流水在模型输入、工具进度、错误、缓存、报告和审计中的脱敏规则，须与模型政策及安全契约一致。
- 已知日志来源标签仍需映射为批准的索引、代码仓库与 main/master 分支；当前尚无实际资源范围或访问批准，不能据服务标签猜测映射或访问真实环境。
